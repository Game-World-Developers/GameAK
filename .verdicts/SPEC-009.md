# SPEC-009: Runtime API

**Validation timestamp:** 2026-06-13

**Verdict:** READY

## Assessment

SPEC-009 defines the public API surface of the GameAK Runtime. All six previously identified blockers have been resolved. The spec is now implementable.

## What Changed Since Previous Validation

### Previously Blocked: 6 Issues — All Resolved

| # | Issue | Resolution | Status |
|---|-------|-----------|--------|
| 1 | **Undefined tick execution ordering** | Now explicitly defined: (1) Controllers execute, (2) pending Commands (including those just produced) are validated and executed by the Scheduler, (3) TickResult is produced. Commands submitted between ticks are queued for the next `tick()`. | ✅ |
| 2 | **Undefined allocator interface** | Removed from v1 configuration. The config object now contains only log level. Future versions *may* introduce allocator customization. | ✅ |
| 3 | **Undefined block capacity hints** | Removed from v1 configuration. Future versions *may* introduce capacity hints. | ✅ |
| 4 | **Undefined sensible defaults** | Default configuration values explicitly documented: Log level defaults to `warn`. | ✅ |
| 5 | **Undefined ExecutionStatus** | Enumeration explicitly defined: `enum class ExecutionStatus : uint32_t { Success, PartialFailure, CriticalFailure }` with clear semantics for each value. | ✅ |
| 6 | **Undefined type descriptor structure** | `BlockTypeDescriptor` struct explicitly defined with `type_id`, `size`, `alignment`, and `name` fields. Rules for `type_id` uniqueness and registration errors documented. | ✅ |

## Cross-Reference Verification

All API concepts referenced in SPEC-009 are defined in companion specs:

| Concept | Definition Location |
|---------|-------------------|
| **Controller** | SPEC-010: Callable type accepting state view + command producer, returning Result |
| **Command** | SPEC-007: Immutable state modification request, executed by Runtime |
| **Runtime Identity** | SPEC-008: 64-bit class type wrapping uint64, generated by Runtime |
| **Data Block** | SPEC-006: Smallest addressable unit of simulation state, data only |
| **Result type** | SPEC-012: Discriminated union containing value or error, `[[nodiscard]]` |
| **Scheduler** | SPEC-011: Validates, orders, and executes Commands (default FIFO) |
| **TickResult** | SPEC-009: Described with fields (commands executed, rejected, controllers executed, ExecutionStatus) |
| **ExecutionStatus** | SPEC-009: Enum defined with Success, PartialFailure, CriticalFailure |

## Remaining Observations (Non-Blocking)

- **TickResult is described but not formally `struct`-defined**: The spec lists TickResult's contents (commands executed, commands rejected, controllers executed, execution status) and defines ExecutionStatus as an enum. A developer can infer the exact struct:
  ```cpp
  struct TickResult {
      uint32_t commands_executed;
      uint32_t commands_rejected;
      uint32_t controllers_executed;
      ExecutionStatus status;
  };
  ```
  The semantics are unambiguous; the exact member naming is the only freedom.

- **Result success value types**: The spec says creation, destruction, and command submission "must return a Result type" but does not specify what the success value is for each (e.g., creation returns the new block's Runtime Identity; destruction returns void). This is a minor detail inferable from context: creation generates an identity per SPEC-008, so the Result carries it; destruction and submission succeed with void.

- **Controller execution order**: SPEC-009 does not specify the order controllers execute in. This is intentional per SPEC-010 ("Controller execution order is determined by the Runtime"). The developer has freedom to choose (e.g., registration order) as long as it's deterministic.

## Open Questions

All resolved. No unanswered questions remain.

## Notes

- The `Status: DRAFT` header in the spec should be updated to **READY** once implementation begins.
- The tick ordering guarantee ("given the same state and same Controllers, the same Commands are produced and applied in the same order") provides the determinism foundation that SPEC-003 requires.
- Configuration is intentionally minimal for v1 — the design is extensible for allocator customization and capacity hints in future versions.

## Final Determination

**SPEC-009 is READY for implementation.**
